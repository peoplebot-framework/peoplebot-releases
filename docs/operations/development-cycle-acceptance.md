# Development-cycle acceptance checklist

## Specified and implemented

- Strict exact task plus separate local authority binding; unselected input cannot dispatch.
- Distinct coordinator, implementer, and reviewer Instances using common admission.
- Unique ordinary attempt branch/worktree at the accepted base, host-verified path
  allowlist, fixed verification commands, deterministic candidate commit, and
  compare-and-swap private candidate ref. Failed partial work remains inspectable.
- Existing exact-commit supplied-context project reviewer; stale candidate reviews stop.
- Durable import/stage/candidate/review/result progress and pre-launch invocation reservations.
- Bounded nonzero-child diagnostics that retain safe classification, event/process
  distinctions, stream fingerprints and available usage through terminal evidence
  and coordination reporting without retaining raw provider or process content.
- Per-invocation progress reports bind environment/machine, task/Execution/role,
  launch/end/elapsed time, outcome, process/response facts, model/runtime when known,
  exact evidence and emitted provider counters; unavailable measurements stay unknown.
- One finite invocation allowance and elapsed limit shared by corrections.
- Serialized selected-task publication/discovery, explicit Instance-memory checkpoint,
  sovereign correlated reply publication, and verified append-only coordination export.
- Exact requirements/request/diff/verification review packet and validated finding input
  for an allowed correction, plus a manifest of explicitly selected exact candidate
  source files supplied to the reviewer.
- Direct candidate-ref checks, exact verified-tree commit construction, remaining-time
  clipping, and preservation of known results across later progress-save failures.
- Verification ownership uncertainty retains the exact worktree and recovery authority;
  successful verification continues to remove it.
- Exact reader recovery uses the common admission owners, byte/exact-State evidence
  guards and one append-only reconciliation record; it refuses changed evidence or
  live ownership and does not replay or refresh the stopped task.
- A halted cycle whose message differs from the newly imported request cannot be
  rendered or exported as that new request's response.

## Offline verified

- Run `python docs/examples/development_cycle_fake.py` from a committed checkout.
- Focused tests cover the real production command/orchestration and both actual Adapter
  wrappers with fake process responses, real synthetic Git candidates and local remotes,
  explicit memory save/resume, published correlated replies, and a fresh OS-process
  continuation with no redispatch. Captured provider inputs contain exact requirements,
  diff/verification evidence and, for correction, validated prior findings.
- Failure assertions cover symbolic refs, HEAD/content changes, deadline expiry before
  verification/review/correction, interruption after reservation, stale review,
  candidate/review progress-save failures, missing terminal evidence, duplicate
  reconciliation, uncertain publication, conflicting export, and unresolved verification
  ownership with the exact worktree retained.
- The actual development command composition preserves a fake stopped attempt with an
  allowed partial checkpoint, records its terminal failure and usage, then lets a
  distinct task start from its own accepted base and reach fake implementer/reviewer
  providers without reader repair. Results remain correlated to their own requests.
- Existing lifecycle tests continue to cover busy admission, stop, exhausted cycle,
  uncertain owner publication, terminal persistence failures, and no redispatch.

## Live adoption boundary

No active authority, task, provider-session binding, repository destination,
credential, memory base, status path, STOP path, or candidate ref is distributed.
The owning environment must create and review those values, keep live gates off
until separately authorized, and invoke one exact task with a unique Execution ID.

A minimal two-call task uses `maximum_invocations: 2`,
`maximum_corrections: 0`, `per_invocation_timeout_seconds: 900`, and
`maximum_elapsed_seconds: 1800`: one implementer and one reviewer call. A finding
stops unless the separately approved task explicitly budgets a correction.

## Not live verified

The deterministic release checks use fake providers and synthetic repositories.
They do not establish a successful live provider-backed development cycle. One
historical supervised private attempt stopped at an ordinary implementer-process
failure and was preserved without automatic retry; it is not an acceptance claim.
A consuming environment must separately verify its provider responses, normal Git
writes, exact candidate/review/memory States, message publication, scheduler
identity, locked-desktop behavior, and timer evidence.

Linux bridges may reuse the same Python development command, progress schema, ordinary
attempt-branch convention and structured Codex usage extraction after adopting the exact
reviewed source. Absolute paths, runtime roots, executable/Codex-home bindings, process
ownership, local credentials and any scheduler integration remain host-owned and must be
measured separately. This Windows change does not update or attest either Linux installation.
