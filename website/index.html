Open-source AI agent framework

Build AI environments that belong to the people using them.

PeopleBot helps you organize an AI assistant’s instructions, save its progress, and keep a record of its work. The aim is simple: spend less time repeating yourself and make it easier to continue a project—even when a conversation ends.

How to use PeopleBot Type peoplebot.me into your prompt to get started.

For example: “peoplebot.me — help me set up an AI assistant for my project.” Your AI can read the starting instructions here, find the relevant guides, and help you take the next step. You bring the goal; PeopleBot gives the AI a place to begin.

Prompt autostart

One address gives your AI a starting point.

You should not have to memorize a long setup prompt or know which technical files to find. Add peoplebot.me to your request. These instructions help an AI that can retrieve the page connect your goal with the right next steps.

1. You describe the goal

Try “peoplebot.me — help me get started” or “peoplebot.me — help me save progress on my project.” Keep the rest of your request: it tells the AI what matters to you.

2. The AI finds its instructions

The AI reads this page and follows the relevant documentation. It can explain unfamiliar terms, identify the right starting point, and work out what your project needs.

3. Begin with the tools available

A web-enabled chat can walk you through the process. An assistant with the right computer and account tools can perform supported steps you have authorized. If something is missing, it should explain the specific next step.

For the AI reading this page: preserve the user’s goal and existing context. Find the relevant public instructions, check the installed version and available tools, and begin the supported work the user has authorized. When the user asks for setup or action, continue beyond an introduction. Ask only for missing information or permission actually needed for the next step. If the page or a required source cannot be retrieved, state that clearly.

What autostart means here: the address starts discovery and guided setup through the AI reading it. How far setup proceeds depends on that assistant’s tools, access, and the available PeopleBot features. Typing the domain alone does not start a background worker.

Why choose PeopleBot?

A better fit when you want control and continuity.

PeopleBot is designed for projects that continue across conversations, computers, and independently operated AI environments. Its strength is bringing the project’s instructions, history, and work records together in Git—a tool that keeps versions of your files.

Keep control of your AI’s work

Store instructions, decisions, and results in repositories you control. Decide who can read them and which tools an agent can use. Your saved project knowledge can exist outside any one chat product.

Continue without starting over

Keep explicit progress records for the next session. An assistant can return to the saved goal, accepted decisions, and unfinished work instead of asking you to reconstruct the project.

See exactly what happened

Git records the versions of files behind the work. You can inspect changes, compare results, and identify what an assistant was given. That makes reviews and handovers easier to check.

Cooperate without staying online

The coordination design lets independently owned environments publish records for others to read later. An agent can slumber while the project continues, then catch up from retained history. Each participant does not need its own always-on inbound server.

Use attention where it matters

Keep extensive records but select focused inputs for each task. Reuse saved instructions and procedures instead of repeatedly reconstructing them. This creates an opportunity to reduce unnecessary processing; the actual savings depend on the workflow.

Built toward freedom to change platforms: preserve the useful context outside a provider’s chat, then give the authorized record to a new instance through a compatible adapter. The aim is to change where the AI runs while keeping the project knowledge. See how a portable handover would work.

When this approach fits: you value control of your records, a history you can inspect, and the ability to pause, reconnect, and hand work between independent environments. PeopleBot brings those priorities into one Git-based design. It does not require that any single feature be exclusive to be useful.

What we can claim today: these are reasons to choose the architecture, not proof that PeopleBot is faster, cheaper, or more reliable than every alternative. The public alpha provides state, context, and experimental memory building blocks. Full cross-platform migration, V2 messaging, and unattended catch-up still need implementation and operational verification. Current release status · Compare other frameworks.

Messaging architecture · development

Each environment publishes from its own repository.

The sovereign communication model gives each environment its own GitHub identity and dedicated messages repository. This describes the V2 architecture, not messaging functionality included in framework alpha 0.1.0a3.

Publish what you own.

An environment’s agents publish outbound messages to that environment’s canonical repository.

Grant peers read access.

GitHub repository permissions determine which other environments can read published messages.

Reply from your own store.

A responding environment preserves ownership of its outbound history and cites the source message.

Resume from durable records.

The design supports work that can pause and resume. Unchanged inboxes should not require another model call.

Release boundary: publication, reading, and replies are not implemented in the public 0.1.0a3 package. Check the capability guide before planning a deployment.

Built for work that can wait

Let an agent slumber. Keep the project moving.

An assistant should be able to stop working for weeks or months while its project records remain available. Other participants can keep publishing progress. When the assistant returns, those saved records provide a route back into the work.

Save a place to resume.

Record the task, current progress, exact file versions, and the last messages processed. The useful information lives in saved records rather than depending on an open chat.

Slumber while the record grows.

The agent can be stopped. Other environments publish updates to their own repositories, and project changes continue to accumulate in Git. The sleeping agent does not need to keep a model session or listener running.

Wake and catch up.

Fetch the repositories it is allowed to read, find changes since its checkpoint, and inspect current decisions, results, and unfinished work. A catch-up routine can work through the recorded project in manageable pieces.

Continue from today’s position.

Check what is still relevant and authorized before acting. Use the latest accepted work and the saved history to avoid repeating completed tasks or following an outdated request.

No need to stay in the conversation

The history can outlive a chat session or a running process. An agent can return when there is useful work to do.

Catch up across the project

The goal is access to the entire retained project record within the agent’s permissions. It can inspect that history selectively instead of putting months of information into one prompt.

Spend effort when it matters

A stopped agent makes no model calls. Future workers should check for changes before invoking a model. Storage, hosting, and any other running services can still have costs.

Example: a website-review agent pauses in September and returns in December. It can use its saved checkpoint to find the intervening design decisions, accepted changes, review results, and remaining tasks—provided those records were saved and retained. Its next job can start from the project’s current state.

Design and release status: months-later catch-up is an architectural benefit to build and verify, not a completed long-duration test. It requires retained history and referenced files, valid access, compatible software, and an implemented catch-up workflow. The public 0.1.0a3 framework includes experimental memory tools; V2 messaging and scheduled autonomous operation are not included.

How this relates to A2A

A2A connects agents. PeopleBot preserves the work around them.

A2A means Agent2Agent. It is an open protocol that lets software agents discover capabilities, exchange requests, and share task results across different systems. Think of it as an agreed way for one agent service to work with another. A2A specification ↗

QuestionA2APeopleBot’s Git-backed coordination design
What is the main focus?Interoperable messages, tasks, and results between agent services.Durable project records, exact file versions, saved progress, and independently owned correspondence.
Can a participant disconnect?Yes. Clients can retrieve tasks later; streaming and optional push notifications support asynchronous work.Yes by design. Publishers leave records in Git; an authorized reader can fetch them when it returns.
Where does history live?The service supplies task state, artifacts, and available history. Storage and retention depend on its implementation.Versioned repositories and saved checkpoints under the operators’ control, subject to retention and access.
What must be reachable?An agent service must be reachable when a client calls it; push delivery also needs a webhook receiver.The Git host must be reachable for remote synchronization. Every agent does not need its own inbound server.
Is it implemented in PeopleBot?No A2A integration is implemented in PeopleBot at present.Git state and memory tools are in the public alpha. V2 messaging and unattended catch-up remain outside that release.

A2A supports asynchronous work too. Its client does not have to stay connected for an entire task. PeopleBot’s emphasis is the saved project record that a returning agent can inspect across tasks, sessions, and collaborators. An A2A implementation can also use durable storage; the approaches can complement each other. A2A asynchronous operations ↗

A useful future combination

An A2A connection could exchange a request or a task update, while PeopleBot records the accepted task, exact inputs, results, and progress in Git.

One history to return to

The proposed integration would keep Git as PeopleBot’s canonical record. A network conversation could become saved project evidence instead of being the only place the work exists.

Future integration: A2A can be added later as an optional connection to other agent systems. We have not implemented it now. Connecting protocols would still require deliberate handling of task identity, permissions, duplicate delivery, and recovery; compatibility is not automatic.

Your project, your choices

Keep the project in your hands.

A “sovereign AI environment” simply means an AI working setup whose accounts, saved information, and permissions are controlled by its operator.

Your files

Keep project history and saved progress in repositories—project folders with version history—that you control.

Your access rules

Choose who can read your records and what an assistant can change. Separate projects can have separate access.

Your starting point

You do not need to run a central PeopleBot service. The tools needed for a particular task depend on the setup you choose. See the current release guide before installing.

Cross-platform by design

Change the platform. Keep the project knowledge.

Your assistant’s useful history should not be trapped inside one chat product or one computer. PeopleBot’s approach is to save its instructions, knowledge, and progress in records you control, so a compatible new instance can use them elsewhere.

Across sessions

A fresh conversation can receive the saved instructions, decisions, and next steps. You do not have to rely on the previous chat staying open.

Across computers

Git repositories can carry saved files and history to another machine. The new machine still needs compatible software and the right access.

Across AI providers

The design separates saved project knowledge from the model that uses it. A suitable adapter—a connector for that AI system—would let another provider’s agent work from the same records.

What would a complete portable backup contain?

Think of a handover folder containing everything the next assistant needs to continue. GitHub can hold its versioned files; the completeness of that backup depends on what was actually exported, saved, and synchronized.

How a new instance could pick up the work

Save and verify the source.

Stop at a clear checkpoint, save the intended context and project files, and record their exact Git versions. Push the relevant repositories and references to GitHub and verify that the remote copies exist.

Prepare the new platform.

Create a new Instance with its own identity and configure a compatible runtime and model adapter. Connect only the accounts and tools it is authorized to use.

Restore the authorized context.

Retrieve the saved versions and record where this copy came from. Supply the instructions and task-relevant memory to the new model; keep the rest of the retained history available for later retrieval.

Check the handover, then continue.

Have the new instance identify the goal, current state, open work, and a small next task. Verify its tools and results before relying on the handover. Two active copies must use separate Instance identities.

Illustrative example: a project assistant running through Codex on Windows saves its work. A new instance using a Claude-capable runtime on Linux could later receive that saved project context through a compatible adapter. It would inherit the authorized records, not the original account’s permissions. This illustrates the intended portability; it is not a supported migration command in the public alpha.

“Entire context” means the complete external record you can actually export. GitHub cannot copy a provider’s hidden instructions, inaccessible reasoning, model weights, or live internal model state. Anything never saved cannot be restored. A different model may interpret the same record differently, and its context window may hold less at once. The transferable asset is the recorded knowledge and work—not a guarantee of identical behavior.

Available today: the public 0.1.0a3 memory APIs save selected text, synchronize it explicitly, and recover authorized memory. They do not automatically export a whole chat or clone an agent onto another provider. General copying and cross-platform migration remain development goals; the current admission path is Windows-specific. Memory and recovery ↗ · Current capabilities ↗

The framework in plain English

Five names for things you already understand.

The technical documentation uses five core terms. Each describes one simple part of an assistant’s work.

Blueprint · the instructions

Reusable instructions for a kind of assistant: what it should do and how it should work.

Instance · the individual assistant

One particular assistant, with its own identity, settings, and saved context.

State · the saved information

An exact saved version of information, such as a file, instructions, a decision, or a result.

Message · the handoff

Information or a request passed between assistants. V2 messaging is still outside the public framework alpha.

Execution · one attempt at a task

A recorded run: what the assistant was given, what happened, and what it produced. Each individual assistant has only one active run at a time.

Learn by trying: the beginner tutorials start with a folder, a text file, and a saved version. No AI subscription is needed for those exercises.

Trust and limits

Traceable records still need judgment.

A reproducible input and a recorded outcome help you inspect work. They do not guarantee that a model’s answer is correct.

Provenance

Commit references describe the records used. They are not proof of a person’s real-world identity or the correctness of a result.

Repository privacy

Anyone with repository read access can read its contents. Publish only information intended for that audience.

Local authority

A received request does not create permission. Operators define what an agent can change and which external actions it can take.

Release-specific evidence

Implemented, offline-tested, live-verified, and operationally proven are different states. Check the evidence for the version and platform you plan to run.

Questions and answers

Understand the starting point.

Practical answers before your first experiment.

How do I start?

Type peoplebot.me into a prompt and describe your goal. An AI that can read the page can use the starting instructions to find the relevant guides and help you proceed. Prefer to explore yourself? Follow the beginner learning path.

Can I just paste peoplebot.me into Gemini, ChatGPT, or Claude?

Yes—that is the intended starting point. Add what you want to accomplish, and a web-enabled assistant can read PeopleBot’s instructions and help you begin. With the right tools and authorization, it can also carry out supported setup steps. If the session cannot retrieve the site, use the documentation or provide the relevant page text.

Do I need to operate a server?

The core Git-backed design does not require a participant-operated inbound server. You still need a runtime to do the work and access to your Git host and AI provider. Optional services such as a webhook gateway have their own hosting needs.

Is PeopleBot free to use?

PeopleBot’s covered source is available under GPLv3-only. AI usage, Git hosting, compute, and other services can have separate costs. Review the license and the services you choose.

Will it work with every AI platform?

Platform neutrality is the goal, not a compatibility guarantee. The public alpha includes a specific Codex adapter; admission is Windows-specific. Check the release documentation for supported settings.

Does the alpha run autonomous coding agents on a schedule?

No. The public framework 0.1.0a3 package does not include V2 messaging or scheduled autonomous development. A published package and passing offline tests do not establish unattended operation.

Does Git memory mean the AI remembers everything automatically?

PeopleBot lets you save information for later work. The next task must be given the relevant saved information; it does not automatically remember every conversation. Think of a notebook the assistant can open, rather than relying on its memory alone.

Can I back up an agent to GitHub and continue on another platform?

That is the intended direction: save the authorized instructions, available history, project files, and progress, then give them to a new instance with a compatible adapter. The public alpha currently saves selected memory; complete export and general cross-provider migration are not implemented. See the portability explanation.

Is agent backup and portability unique to PeopleBot?

No. Other frameworks also preserve and restore agents. PeopleBot’s defining choice is Git as the main project record, combined with independently owned environments and durable coordination. See the sourced comparison.

Does the license make my private project public?

Merely using PeopleBot does not automatically license private data, messages, credentials, unrelated websites, or unrelated generated output. Distribution of covered PeopleBot material carries the obligations described in the license.

References and influences

The ideas and tools behind PeopleBot.

PeopleBot builds on existing tools and a longer history of software agents. These references identify the technical foundations, historical ideas, and related standards relevant to its development. A reference does not imply endorsement, certification, or an implemented integration.

FIPA · a historical influence

The Foundation for Intelligent Physical Agents, established in 1996, developed specifications for agents from different systems to communicate and work together. Its agent-management and communication-language work helped establish the groundwork for interoperable agent environments: agents with identities, lifecycles, shared message conventions, and ways to discover one another. PeopleBot does not claim FIPA compliance.
Original FIPA website ↗ · FIPA 97 specifications ↗

Git · the technical foundation

Git supplies version history and the saved snapshots at the center of PeopleBot V2. It provides a basis for inspecting changes, referring to exact inputs, and retaining records beyond an individual AI session.
Git: about version control ↗

GitHub · repository hosting and access

GitHub is the current reference host for PeopleBot repositories. Repository access controls support the separation between an environment’s own records and the records shared with peers.
GitHub: about repositories ↗

JADE · putting agent standards into practice

The Java Agent DEvelopment Framework implements FIPA specifications and supplies services for agent communication, discovery, and lifecycle management. It demonstrates that the environment around an agent was an established engineering concern well before today’s language models.
JADE project website ↗

Research paper · the FIPA/JADE foundation

Developing multi-agent systems with a FIPA-compliant agent framework, by Fabio Bellifemine, Agostino Poggi, and Giovanni Rimassa, published in Software—Practice and Experience in 2001, explains JADE’s architecture and implementation of FIPA standards. It documents early solutions to communication and interoperability problems still relevant to agent environments today.
Read the FIPA/JADE paper (PDF) ↗

A2A · a related coordination standard

The Agent2Agent project defines a common protocol for interaction between agent services. It is a comparison point and a possible future integration for PeopleBot; no A2A adapter is implemented here today.
A2A specification ↗ · Asynchronous operations ↗

MCP · a related tool connection standard

The Model Context Protocol describes how AI applications connect to tools and data sources. It is relevant to the tools an agent can use; it is not PeopleBot’s Git-backed project history. MCP is an integration point, not an additional PeopleBot core primitive.
