# Finite work cycle v0

`peoplebot.work_cycle.run_work_cycle_tick` performs at most one task. It loads messages from explicitly bound peer sources, selects the oldest eligible task, maps its purpose through a caller-owned `TaskPolicy`, and invokes only a handler present in the caller's local registry. Message content never names a process or extends the local allowlist.

The tick holds a work-cycle ownership admission for its whole lifecycle while composing with the existing per-Instance execution admission. That logical owner remains held through handler return, memory checkpointing, reply publication, and final reader-progress persistence, while the nested memory operation can acquire the normal Instance admission without deadlock. A competing tick for the same Instance is refused until all post-handler work finishes.

The tick uses a finite completed-task limit and writes durable reader progress to a deterministic local direct ref before invoking a handler. Persisted claimed, unresolved, and accepted-stop outcomes are durable barriers: later ticks expose the original exact message/reply/memory/progress evidence and dispatch nothing until an authorized operator performs a future explicit recovery action. No automatic clear, retry, budget reset, or recovery service exists. This is deliberately at-most-once local dispatch and does not imply exactly-once effects. Final dispositions are completed, failed, unresolved, or stopped. No-work results are idle, busy, stopped, or exhausted. Idle, busy, stopped, and exhausted paths never invoke a handler/provider. The completed-task limit is only a retained-result bound; it is not a live invocation, elapsed-time, recurrence, or provider-spend budget. V0 bindings must assign one inbound task stream to one designated Instance: separate Instance progress refs do not provide cross-Instance claiming for the same stream.

Handlers may return exact States and bounded memory items. A caller can supply a checkpoint callback composed from the existing explicit Instance-memory API. The correlated reply includes the exact saved memory State when successful. Recovery tests reconstruct bindings, durable reader progress, exact memory State, and a fresh tick in a separate Python process. They prove exact memory retrieval, no redispatch after completion, and durable halts after interrupted claims, unresolved publication, and accepted stop messages while another task is waiting.

After handler/checkpoint/publication work, terminal progress and compact status are each attempted once. A terminal-progress failure returns `cycle.terminal_progress_persist_failed` with the original outcome and all independently known message, reply, and memory States, while identifying the last known durable progress State without claiming the terminal update succeeded. A later status-write failure returns a bounded in-process `cycle.status_persist_failed` or combined `cycle.progress_and_status_persist_failed` diagnostic with `status_persisted=false`; it is available to the caller/CLI but is explicitly not durable. Neither failure retries the handler or publication, overwrites conflicting progress, or releases the durable claim barrier.

`load_cycle_bindings` accepts only `peoplebot.cycle-bindings.v0` JSON with absolute runtime, checkout, status, and stop paths; one local owner destination; one to eight peer sources; and the deterministic progress ref. `load_task_policy` accepts only `peoplebot.task-policy.v0`, one to sixteen purpose/handler routes, a 1–256 completed-task limit, and an explicit stop-message choice. Both configurations are capped at 64 KiB and reject extra fields.

The CLI command `peoplebot work-cycle-tick` writes a sanitized `peoplebot.work-cycle-status.v0` file bound to its exact execution ID. Status includes whether terminal progress and status persistence succeeded plus the original outcome when persistence changes the returned disposition. If the status destination fails, the same bounded non-durable diagnostic is emitted on standard output and exits unresolved. The only bundled handler is `fixture.complete`, available solely with `--offline-fixture`; production handler binding remains a caller responsibility through the library API. Exit codes are 0 for completed/idle/stopped, 10 busy, 11 exhausted, 12 failed, 13 unresolved, and 14 an unsupported disposition.

This is a finite dispatcher, not a workflow engine, planner, arbitrary-command runner, model-process owner, or automatic retry service.
